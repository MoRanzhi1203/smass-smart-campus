## 1. 为什么需要单独的授权

PM0–PM8 已证明（**全部基于合成数据**）：

| 已证明 | 证据 |
|---|---|
| 旧密码格式兼容（单次/双重 MD5 + 懒惰升级） | PM1，29 例 |
| 行迁移幂等与对账 | PM3，tiny/1k/10k 均 strict_ok |
| 双写补偿零残留 | PM4，11 项检查 |
| 完整升级 + 备份恢复 | PM5，tiny/1k 均 exit=0 |
| 性能与多进程并发 | PM6/PM7，死锁 0 |

**未证明**：真实 `app01_*` 行能否无损迁移。

差异在于真实数据可能有合成生成器没覆盖的形态：
- 姓名含生僻字/多音字（生成器只用了 10 姓氏 + 10 天干）
- 证件号历史格式（旧 15 位？含 X 的大小写？）
- 手机号为空/异常值（生成器全填 `000%`）
- 班级/学院引用断裂的**真实**模式（生成器只造了 1 条孤儿）
- 密码哈希的实际分布（生成器按 50/20/30 人为分配）

这些只能用真实数据验证，因此需要授权。

## 2. 数据分类与列级清单

### 2.1 明确**不索取**的列

| 表 | 列 | 原因 |
|---|---|---|
| `app01_admin/student/teacher` | `password` | **密码哈希属于凭据**。PM1 已在源码层证明兼容逻辑，无需真实哈希。若需验证，可由数据责任人在**其环境内**跑一次抽样校验并**只回报布尔结果** |

**本申请不包含任何密码哈希的导出、复制或比对。**

### 2.2 需要读取的列（按敏感度分级）

| 级别 | 列 | 用途 | 处理方式 |
|---|---|---|---|
| **P2 高敏** | `app01_student.cardID`、`app01_teacher.cardID` | 验证 18 位约束与唯一性 | **读出即脱敏**，只保留长度与前 2 位 |
| **P2 高敏** | `app01_student.phone`、`app01_teacher.phone`、`qq` | 验证可空性 | 只保留"是否为空"与长度分桶 |
| **P1 中敏** | `app01_student.name`、`app01_teacher.name`、`app01_admin.name` | 验证长度/字符集 | 替换为 `REAL-{序号}` |
| **P1 中敏** | `app01_student.address` | 验证长度 | 只保留长度 |
| **P0 运营** | `id`、`classes_id`、`college_id`、`political`、`sex`、`nation`、`entry_time` | 迁移映射与 FK 完整性 | 原样（非个人标识） |

### 2.3 需要的表

```
app01_admin, app01_student, app01_teacher,
app01_college, app01_major, app01_classes, app01_grade
```

**不需要**：`auth_*`、`django_*`（除 `django_migrations` 的计数）、
任何其他业务表。

## 3. 最小可行样本

| 维度 | 要求 | 理由 |
|---|---|---|
| 行数 | **≥ 50 且 ≤ 200** | 足够覆盖角色与学院交叉，不足以构成批量泄露 |
| 角色覆盖 | admin ≥ 1、teacher ≥ 5、student ≥ 30 | 三类都要有 |
| 学院覆盖 | ≥ 2 个不同 `college_id` | 验证 scope 隔离 |
| 班级覆盖 | ≥ 3 个不同 `classes_id` | 验证层级 |
| 边界样本 | 姓名最长/最短、地址最长、phone 为空、(若有)FK 断裂行 | 覆盖真实形态 |
| 样本选择 | **按 id 排序取前 N**（可复现、不含主观挑选） | 避免"挑好看的行" |

**不索取全量。** 若 50–200 行迁移成功，剩余行的风险属于"同分布重复"，
可由数据责任人按同样规则自行验证。

## 5. 读主体与最小权限

| 项 | 要求 |
|---|---|
| DB 账号 | **新建专用只读账号**（如 `smass_pmr_real_ro`），不复用 `root`、不复用 `smass_g5_ro` |
| 权限 | `SELECT` 仅限 §2.3 列出的 7 张表；**无** `INSERT/UPDATE/DELETE/CREATE/DROP` |
| 连接来源 | 仅本机 `localhost`（`host` 限定），不允许远程 |
| 有效期 | 与 §7 的 TTL 一致，演练结束即 `DROP USER` |
| 审计 | 开启 MySQL general log 或应用侧记录每条 SELECT（谁、何时、哪张表） |

**权限验证**（执行前必做）：用该账号尝试 `CREATE TEMPORARY TABLE`，**必须被拒绝**。

## 6. 脱敏方法（读出即脱敏，不落原值）

| 原字段 | 脱敏规则 | 保留的可测属性 |
|---|---|---|
| `name` | 替换为 `REAL-{序号}` | 长度分桶（≤4 / 5-8 / >8） |
| `cardID` | 只保留 `LEN` 与前 2 字符 | 长度、前缀字母/数字 |
| `phone` | 只保留 `LEN` 与"是否为空" | 长度、可空性 |
| `address` | 只保留 `LEN` | 长度 |
| `qq` | 只保留 `LEN` 与"是否为空" | 同上 |
| `password` | **不读取** | — |

**实现要求**：脱敏发生在 SELECT 之后的**同一进程内存**，
写入隔离库前原值不得落盘、不得进日志、不得进临时文件。

## 8. 一次性真实行演练 runbook

### 前置检查（全部通过才可开始）

```
[ ] §4 审批矩阵全部签字
[ ] 只读账号创建并验证写被拒
[ ] 目标库名已登记且不存在
[ ] 脱敏脚本经安全负责人 review
[ ] 演练窗口已通知 DBA
```

### 步骤（双人复核：操作者 + 复核者）

| # | 步骤 | 复核点 |
|---|---|---|
| 1 | 记录 `smass` 26 表行数 + 结构指纹 + 数据指纹 | 复核者确认基线 |
| 2 | 用只读账号 `SELECT` 50–200 行（按 id 排序） | 确认 SQL 只含 §2.3 的列 |
| 3 | 同进程内脱敏，写入 `smass_pmr_real_<ticket>`（26 表结构） | 抽查 3 行确认无原值 |
| 4 | 跑 PM3 行迁移到 `smass_pmr_target_real_<ticket>` | `strict_ok=true` |
| 5 | 跑 PM5 升级 + 备份恢复 | 双指纹一致 |
| 6 | **密码兼容性**：由数据责任人在其环境内跑抽样校验，只回报布尔 | 本项目**不接触哈希** |
| 7 | 记录结果到 `docs/SMASS_PMR_Real_Data_Drill_Result.md` | 复核者签字 |
| 8 | 销毁隔离库与只读账号 | 复核者确认 |
| 9 | 复检 `smass` 指纹未变 | 三项 unchanged |

### 中止条件（任一触发立即停止）

- `smass` 指纹变化
- SQL 出现 §2.3 之外的列
- 脱敏后仍发现原值（抽查失败）
- `strict_ok=false` 且原因不明
- 只读账号出现任何写权限
