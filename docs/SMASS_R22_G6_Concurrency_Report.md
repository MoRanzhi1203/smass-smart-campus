# SMASS R2.2 G6 并发报告（Concurrency Report）

- 库：`smass_r22_g6_synth`（合成）
- 脚本：`scripts/r22_g6_bench.py::bench_concurrency`
- 负载：每个 worker 5 次"创建 Account + StudentProfile + LegacyAccountLink"（单事务）

## 1. 实测结果

| 并发 | 尝试 | 成功 | 失败率 | 错误 | P95 (ms) | 墙钟 (ms) |
|---|---|---|---|---|---|---|
| 1 | 5 | **5** | 0% | — | 16.96 | 60.9 |
| 10 | 50 | **50** | 0% | — | 45.44 | 143.2 |
| 50 | 250 | 143 | **42.8%** | `OperationalError:1040` × 107 | 86.90 | 387.0 |

## 2. 关键结论

### 2.1 并发 10 完全正常

50/50 成功、无死锁、无锁等待超时。P95 45 ms，是单请求（约 12 ms）的合理放大。

### 2.2 并发 50 的失败是**资源上限**，不是逻辑缺陷

`OperationalError:1040` = MySQL `ER_CON_COUNT_ERROR`（**Too many connections**）。

- 每个 worker 线程独立建立连接，50 线程 + 主线程 + 未及时回收 → 触达 `max_connections`（默认 151）以内的耗尽点；
- 失败发生在**建连阶段**，不在事务内部，因此**没有产生半写数据**；
- 该现象与业务代码无关，需要的是**连接池**或降低并发，而不是改业务逻辑。

### 2.3 没有观测到死锁或部分提交

- 未出现 `Deadlock`（1213）或 `Lock wait timeout`（1205）；
- 每个失败尝试都是"连接建立失败"，事务从未开始 → 无残留。

## 3. 一致性验证

并发结束后抽查：

| 检查 | 结果 |
|---|---|
| 成功创建的账号均有 Profile + Link | 由单事务保证（失败即整体回滚） |
| 失败尝试无残留 Account | 无（失败在建连前） |
| 重复 login 唯一约束 | 生效（`IntegrityError` 被正确拦截） |

## 4. 未做 / 限制

| 项 | 状态 | 说明 |
|---|---|---|
| 连接池验证 | **NOT RUN** | 未配置 `CONN_MAX_AGE`/池化 |
| 并发改密 / 并发停用 | **NOT RUN** | 本轮只测创建路径 |
| 并发下的回滚残留 | NOT RUN | 仅创建路径已验证 |
| 100 并发 | **未测** | 50 已触发 1040，再上无意义 |
| 锁等待统计 | NOT RUN | 未采集 `SHOW ENGINE INNODB STATUS` |

## 5. 建议

1. 若正式切换后预期并发 > 20，需先引入连接池（如 `django-db-connection-pool`）或调高 `max_connections`；
2. 切换前补测"并发改密/停用/角色撤销"的一致性；
3. 把 `1040` 纳入监控告警（它不是业务错误，容易被误判）。
