## 3. R4–R10 的真实状态

**没有实现任何 R4–R10 的业务代码。**

原因：每个版本的主题（组织树、学籍历史、课程教学、审批状态机、指标字典、API 版本化、SLO 灾备、发行包）都需要：
- 真实业务规则确认（当前项目没有这些需求文档）
- 独立的数据模型与迁移
- 独立的前后端页面
- 独立的测试体系

按 roadmap §1「不能仅以测试全绿作为发布标准」与用户「不允许空壳模块冒充版本完成」，
本轮**不**为 R4–R10 创建空模块。它们保持 NOT STARTED。

## 5. 后续版本的执行建议（按依赖顺序）

| 顺序 | 版本 | 前置条件 |
|---|---|---|
| 1 | R4 | 确认组织/学籍字段清单与权限矩阵（需业务方输入） |
| 2 | R5 | R4 组织树就绪 + 课程/学期业务规则 |
| 3 | R6 | 审批场景清单（谁审谁、几级、驳回规则） |
| 4 | R7 | 指标字典（每个指标的来源/口径/权限） |
| 5 | R8 | 外部系统清单与协议 |
| 6 | R9 | SLO 目标 + 灾备要求 |
| 7 | R10 | 前六项稳定后 |

**关键**：R4–R10 都受"缺少业务决策"约束（roadmap §12 允许先做可配置骨架并标 ASSUMPTION，
但不能把假设变成生产默认规则）。因此在没有业务输入前，**不宜大规模编码**。

## 6. 结论

- R3 是可交付的真实成果；
- R4–R10 需要业务需求输入，本轮不虚构；
- 若要在无业务输入下推进，建议先做 R4 的**最小通用骨架**（组织树 + 学籍字段元数据），
  并明确标注 ASSUMPTION。
